# E-4: チャンネル単位サンプルキャッシュとリソース会計の整理 — 設計

> **位置づけ**: [列展開の遅延化設計（増分E）](2026-07-24-deferred-column-expansion-design.md) の最終増分。
> E-3（反転）が**オブジェクト数**を根治した（264,004 → 4,324・PR #151）のに対し、
> 本増分は**列読みの対話コスト**と**リソース会計**を扱う。
>
> E-3 の spec は E-4 を「defer 可」と置いていたが、**T9 の実測で defer 不可と確定**した
> （後述 §1）。本 spec はその実測に基づいて E-4 節を全面的に書き直したものである。

## 1. なぜ今やるのか（E-3 出荷時の実測）

E-3 は目標を全て達成した（`prod_demo.mf4` 1,297 MB・実 GUI）:

| 指標 | eager | E-3 後 |
|---|---|---|
| Signal オブジェクト | 264,004 | **4,324** |
| ヘッドレス core 常駐 RSS | 590 MB | **297 MB** |
| USS（主指標） | +281 MiB | **+15 MB** |
| core ロード | 7.0 s | **1.43 s** |
| 実 GUI ロード | 13.1 s | **2.40 s** |
| GUI 定常 RSS | 868 MB | **550 MB** |

**しかし対話コストは 1 ミリ秒も動いていない。** `LazyMdfValues.array()` は列ごとに
「全チャンネル `select` ＋ 全リーフ `_flatten`」をやり直すままであり、E-3 は
オブジェクト数を変えただけだからである。T9 の実測:

- **309–327 ms/列**（最悪ケース = 1,100 列の広幅チャンネル。コストは幅に比例する）
- **5 列で 1,584 ms** — E-4 の目標 448 ms の **3.5 倍**
- この数値は E-3 の spec が目標設定に使った参照帯（333–386 ms/列）に収まる。
  つまり**目標設定の根拠が追認された**のであって、E-3 が前提を変えたわけではない

そして E-3 は**この経路の重要性を上げた**: 1024 ガード退役により広幅 60 チャンネルが
初めて使えるようになり、それらは全て 385 ms/列の重いグループに属する。レーダー物体
リストの兄弟列比較（`Radar.ObjList.dx[0..k]`）はまさにこの形である。

加えて E-3 が持ち越した会計上の負債が 2 つある:

- **エクスポートダイアログの `_selected` が 330,004 キーで +58 MB**（core 削減分の 4 倍）
- **`_resolved_by_key` に上限が無い**（決定 C-g で E-4 へ送った）

## 2. ユーザー決定（2026-07-30）

| # | 論点 | 決定 |
|---|---|---|
| U1 | 同一配列チャンネルの複数列をどう追加するか | **両方する** — 見たい列が決まっているときはまとめて、探索中は 1 列ずつ |
| U2 | 探索ケースのための持続キャッシュの形 | **バイト上限つき LRU**（アイドルタイムアウト式は不採用 — 時間に依らない方がテストが単純） |
| U3 | キャッシュ合計の追加メモリ予算 | **256 MB**（最悪でも GUI 定常 ~806 MB で eager 時代の 868 MB を下回る） |
| U4 | 「すべて選択 → エクスポート」の OOM | **ストリーム化する**（拒否や警告でなく） |
| U5 | 残る「列数の次元」 | **列方向もチャンクして上限なし** |

**U1 からの帰結（簡略化）**: バースト層は不要である。上限つき LRU 1 つが両方の
ワークフローを兼ねる — まとめて 5 列追加すれば 1 列目がデコード済み配列をキャッシュし、
残り 4 列がヒットする。層を 2 つ設けない。

**U5 に伴う前提（コントローラ判断・明示）**: 列方向チャンクは**メモリの天井を外すが、
ディスクと時間の天井は外さない**。330k 列 × 12k 行 ≈ 40 億セル ≈ 数百 GB の CSV（見積）で
実行は数十分〜数時間になる。「上限なし」を成立させるには**進捗とキャンセル**が必要
であり、現在の `ExportController` にはキャンセルが無い。よって進捗・キャンセルを
本増分のスコープに含める（既知の Minor「ハングしたエクスポートが全 unload を永久に
ブロックする」も同じ配線で解消する）。

## 3. アーキテクチャ — 3 つのキャッシュ、3 つの扱い

E-4 が触るキャッシュは 3 つあり、**性質が違うので扱いを分ける**。

| | 中身 | prod 実測 / 見積 | 扱い |
|---|---|---|---|
| **`ChannelSampleCache`**（新設） | デコード済み 2-D 配列 | 広幅 1 本 **96 MB**（12000×1000 float64） | **バイト上限 LRU・自由に evict** |
| `_resolved_by_key` | 鋳造した列 Signal | 1 列 ~96 KB（値込み） | **参照中は pin・それ以外を evict** |
| `_selected`（エクスポート） | ユーザーの選択キー集合 | 330k キー = **58 MB** | **キャッシュではない → 圧縮する** |

### 3.1 なぜ扱いが分かれるか

**`_selected` は evict できない。** ユーザーの意図そのものであり、捨てれば選択が消える。
上限ではなく**表現**を変える — 行レンジ（`(row_index, start, stop)` の集合）で持てば
330k キーが数千タプルになる。

**`ChannelSampleCache` は pin が不要。** 列 Signal が鋳造された時点でその列の 1-D 配列
（96 KB）は `LazyMdfValues._cache` が保持するので、2-D 配列は**次の列を作るためだけ**に
要る。evict のコストは「将来の初回読みが遅くなる」ことだけで、既存のプロットには
影響しない。したがって 256 MB のほぼ全部をここに置ける。

**`_resolved_by_key` は pin が必須。** `GraphPanelVM.render_data` は再描画のたびに
`_signal_map()` を引き直す（レンダーキャッシュのキーに x 範囲・パネル幅・可視キーが
入るので、ズーム/パンで必ずミスする）。プロット中の列が evict されると
**再描画ごとに 316 ms 停止**する。

- **pin 対象**: プロット中・読み値表・範囲統計から参照されている列
- **evict 可**: ブラウザのプレビューで一度覗いた列・エクスポートで読んだ列

### 3.2 所有と配線（案A・採用）

`ChannelSampleCache` を**独立クラス**として新設し、`Session` が 1 個だけ所有して
`MdfLoader` → `MdfHandle` へ注入する。`LazyMdfValues` は既に `self._handle` を持つので、
読み取り時の配線は `self._handle.cache` の 1 段で済む。

**なぜこの形か**: 256 MB は**3 キャッシュ合計**の予算（U3）であり、**予算が 1 つなら
裁定者も 1 つでなければ守れない**。検討した代替:

- **`MdfHandle` が自前で持つ**: 配線ゼロだが予算が**ファイル単位**になり、2 ファイル
  比較で 2 倍になる。U3 を構造的に満たせない → 不採用
- **`LazyMdfValues` 同士が共有エントリを持つ**: 読み取り時の配線は不要だが寿命が拡散し、
  全体予算の強制も teardown 会計も書けない → 不採用

退避規則（pin 規則を含む）を 1 クラスに閉じ込めることで単体テストできる副次効果もある。
ハンドル close で当該ファイル分を落とすのも自然に書ける。

### 3.3 予算の配分

256 MB を固定分割しない。**`_resolved_by_key` の pin 済み分を先に確保し、残余を
`ChannelSampleCache` の LRU が使う**。pin 済み分は現実には数十列 × 96 KB = 数 MB で
あり、「プロットを増やしたら配列キャッシュが縮む」という自然な譲り合いになる。

## 4. エクスポートの 2 次元チャンク

`_rows_shared_timeline` / `_rows_unified_timeline` は現在**全行を `list[str]` に積んでから**
`_atomic_write` へ渡す。メモリを食う箇所は 2 つある:

1. **全信号の同時実体化** — `views = [s.sorted_view() for s in signals]`
2. **CSV テキスト全文の `list[str]` 構築**

### 4.1 行方向（サンプル数の次元）

行ビルダーをジェネレータにし、`_atomic_write` を「行を受け取りながら temp へ書く」形へ。
**②が完全に消える。** これは実際に踏む問題である — `hils` プロファイル（1 ms × 3600 s =
**360 万サンプル**）で **10 信号だけ**エクスポートすると、配列 ~288 MB に対し
**テキストの `list[str]` が ~540 MB**（見積）で合計 ~800 MB になる。

### 4.2 列方向（列数の次元）— 外部転置

CSV は行優先なので、1 行を書くには全選択列の値が要る。行チャンクだけでは①は直らない
（各チャンクで全列が必要なため）。よって**列ブロックごとに部分行を作り、最後に行単位で
連結**する:

```
Pass 1..k:  列を N 本ずつ materialize → そのブロックの「セルだけ」の行を temp へ
            N = 作業予算 / (サンプル数 × 8 B)
Final pass: 全ブロックを行同期で読み、timestamp と連結して本番 CSV へ
```

- **prod**（12,000 サンプル）: 作業予算 256 MB で N = 2,730 列 → **121 ブロック**。
  121 ファイルの同時オープンは問題なく、**1 パスで済む**
- **hils**（360 万サンプル）: N = 9 列 → 36,668 ブロックで FD 上限を超える。
  **ブロック数が上限（200）を超えたら多段マージ**（200 個ずつ中間ファイルへ畳んで繰り返す）。
  再帰は十数行で、これが無いと U5「上限なし」が成立しない

### 4.3 統合タイムラインの最悪項

`lookups = [dict(zip(ts.tolist(), vs.tolist(), strict=True)) for ts, vs in views]` が
**信号ごとに Python dict** を作る。1 本あたり ~2 MB（見積）で 330k 本なら桁が違う。

**`np.searchsorted` に置き換える** — 各列の時刻列はソート済みなので二分探索で足り、
dict は不要になる。

union 自体は安い: **時刻列は物理チャンネルの master で列間で共有されている**ので、
union はチャンネル単位（prod で 4,324 本、`id()` 重複除去後は数本）である。

### 4.4 進捗とキャンセル

U5 を成立させるための条件。`ExportController` にキャンセルイベントを足し、エクスポータは
**列ブロック間と行ブロック間**で確認して temp を片付ける。進捗は
`(完了ブロック, 総ブロック)` で報告する。

## 5. 位置ベース selector

現在 `LazyMdfValues` は `selector=(生リーフ名,)` を持ち、読むたびに `_flatten(...)` を
全リーフ分実行してから 1 本を名前で引く。キャッシュが入ると**ヒット時は 2-D 配列を
位置でスライスするだけ**にできる（`ColumnRecord.spec` からリーフ位置は導出可能）。

E-3 spec は「位置ベース selector は列読みコストの 9–12% しか直さない」としていたが、
それは**キャッシュが無い前提**の数値である。キャッシュ命中時は `_flatten` 全体が消える
ので、命中パスでは支配項になる。

**名前は永続キーのまま保つ**（LD-14 リーフ名は永続キーであり、変更は全保存の無言リネーム
になる）。位置は**ロードごとに導出**し、保存しない。

## 6. teardown 会計

`ChannelSampleCache` の 2-D 配列（最大 256 MB）は現在 `TeardownService._retained_bytes` の
**外**にある。unload 時にこれが同期解放されると FU-16 のフリーズが小規模に再来する。

`remove_group` の戻りに載せて三軸ペーシング（64 MiB / 8,000 信号 / 8 ms デッドライン）に
通す。鋳造列と同じ `columns=` 経路に相乗りできる。

## 7. 衝突診断

`Mat[0]` 衝突（2-D `Mat` の第 0 列と、実在する 1-D チャンネル `Mat[0]`）は最長一致で
実チャンネルが勝つ規則が E-3 で入り、T0 の全数オラクルが test-lock している。しかし
**info 診断は出ていない**（`mdf_loader` の info は「N 本に展開」1 種のみ）。

E-3 spec が要求している 1 件を追加する — 配列側の当該列が**到達不能になる**ことを
ユーザーが知る手段が現在無いためである。

## 8. 公開 API の構造ガード

ブランチ全体レビューの指摘。`dict(signal_map())` への防御は**挙動テスト**（列挙が
鋳造しない）として着地しており、将来 `src/` に `dict(session.signal_map())` が書かれても
コンパイルは通り、**容器のみの map が黙って得られる**。

`tests/gui/test_theme_guard.py`（ratchet allowlist つき AST ガード）と同型のガードを足し、
`signal_map()` の全キー列挙を CI で落とす。

## 9. テスト方針

| 系統 | 何を押さえるか |
|---|---|
| **Layer A（キャッシュ）** | LRU の退避規則（pin 済みは残る・予算超で古い順に落ちる）／位置スライスと名前引きの**値一致**／`np.searchsorted` 置換の値一致 |
| **エクスポート** | 列ブロック分割 × 行ストリームの出力が**現行実装と byte-identical**（これが唯一の安全網）／多段マージが FD 上限を超えない／キャンセルで temp が残らない |
| **会計** | 2-D 配列が teardown の三軸ペーシングを通る（同期解放しない） |
| **構造ガード** | AST で `dict(signal_map())` 形を落とす（sabotage で allowlist を空にして実証） |
| **①gate（realgui）** | 実 OS 入力で「まとめて 5 列追加 → 1 回の select」「探索的に 1 列ずつ → 2 本目以降がキャッシュヒット」を**鋳造カウンタと select 回数**で観測。予算超で古いチャンネルが落ちることも実測 |

**このブランチ系列の教訓を適用する**: 増分B〜E-3 で「実装が効いていることを証明できない
テスト」を実測で 8 件以上摘出した（構造的に空虚な sabotage・到達範囲の主張が誤っていた
sabotage 3 件・**プランの例示コードが自ら実装すると称した決定を一度も満たしていなかった
2 件**・別の例外が先に `pytest.raises` を満たして偶然緑だったテスト・反転で恒真化した
オラクル・「0 ms」を刷って合格する計測）。**各タスクの sabotage は必須**とし、到達範囲は
主張でなく実測で確かめる。

## 10. 出口（受け入れ）

| 項目 | 現在 | 目標 |
|---|---|---|
| 広幅 5 列プロット | 1,584 ms | **≤ 448 ms** |
| `hils` 10 信号エクスポートのピーク | ~800 MB（見積） | **配列分のみ**（テキストはゼロ） |
| GUI 定常 RSS | 550 MB | **≤ 550 + 256 MB**（キャッシュ上限を超えない） |

`--core` モード（E-3 T9 で新設）と実 GUI の両方で測る。**主指標は USS**。

## 11. 非スコープ

- **mmap フロアの削減**（~205 MiB）— 別 follow-up
- **MDF3 が開けない欠陥**（`ValueError: unsupported file_format: 'MDF3'`・LD-02 の記述と
  矛盾）— ユーザーが MDF3 ファイルを持たないため据え置き
- **PC-19 リッチツールチップの復活** — 鋳造しないメタデータ取得口が前提。本増分で
  `has_column` 以上のものは作らない
- **`_selected` 以外の GUI 側メモリ**（E-3 T9 が GUI USS +87 MB のうち ~48 MB を
  未帰属と記録）— Qt/アロケータ残渣であり本増分の外
